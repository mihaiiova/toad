# Toad MCP testing

Toad is a separate testing agent: give it a runnable target, a specific goal, and observable scenarios. Do not assume it has your conversation, project knowledge, server processes, credentials, or approval for side effects. Discover the available Toad MCP tools and their current schemas in your client before calling them; deployed versions may differ from this guide. If the server is unavailable, report that rather than claiming a test ran. If a run reports that Toad is not set up or has no model key, ask the user to run `toad setup` (or `toad doctor` to see what is missing); do not try to fix it yourself.

## Prepare the handoff

1. Inspect the project, relevant instructions, documentation, configuration, and the change to understand what needs testing. Identify the real entry point, working directory, dependencies, startup and build commands, configuration, test data, and observable outcomes. Do not put secret values in the handoff.
2. Decide which behaviors and failure cases matter. Translate them into named scenarios with actionable steps and concrete expected results. Include setup and teardown instructions, preconditions, safe test data, and relevant constraints in the goal, steps, or limitations. State what is out of scope. Ask the user for missing decisions or authorization when you cannot safely infer them.
3. For web tests, supply a reachable URL and ensure the application and required services are running for the duration. `localhost` is relative to Toad's environment; verify reachability rather than assuming it. Prefer staging and test accounts. Disclose any state-changing operations and obtain authorization before actions that affect real data or external services.
4. For CLI tests, supply an absolute working directory and the exact invocation. Determine whether the program needs installed dependencies, network access, input, environment variables, accounts, or writable files. CLI tests run in a copied workspace, not the original project. Setup skips symlinks, `.git`, `.faur`, `.forge`, `.toad`, `.env` files (except `.env.example`), and other credential-like paths; check that the copy will contain what the test needs. Name-based filtering does not catch every secret: ask the user to remove other sensitive files before a copy. Commands usually run in a Linux container (Docker or Podman): choose an image with the program's runtime (`cli.image` in `.toad/toad.yaml` or `target.image`, default `node:22-bookworm`), and remember that dependencies installed on a macOS or Windows host may not run there, so include a build or install step when needed. Put that step in `target.setup` (or `cli.setup` in `.toad/toad.yaml`): Toad runs those commands once in the sandbox before any scenario, records each under `receipts/setup/`, and starts every scenario from the result; a failed setup command ends the run as ERROR (`status: setup_failed`). This is also where to install tools the tests need but the project does not declare (for example a pinned CLI the test suite shells out to). The sandbox's root filesystem is read-only, so install locally (`npm install --no-save pkg@x.y.z`), never globally. Setup and scenario commands run in fresh shells: installed files persist, but `export PATH=...` and `cd` do not. For persistent lookup, set `cli.path: [node_modules/.bin]` (or `api.path`) in `.toad/toad.yaml`, or `target.path` in a handoff or suite: workspace-relative directories are prepended in order for setup and every scenario command; handoff values replace defaults and an empty list clears them. Only configure trusted directories. Alternatively invoke `./node_modules/.bin/tool` or set `PATH="$PWD/node_modules/.bin:$PATH"` in each command. Returned receipt paths are host paths, not mounted into the container: use workspace files for data needed by later commands. Commands run with `/bin/sh`. Without setup, a tester reports a missing program or module as a missing prerequisite (ERROR); set `"allow_installs": true` on the handoff only when it may install one itself and retry. In a container the user's machine is `host.docker.internal`, not `localhost`. On Linux without a container runtime, Bubblewrap shares the host network instead. This is not a hardened sandbox; use trusted workloads.
5. For API tests, supply the base URL and keep the API and its dependencies running for the duration. Requests run in the same sandbox as CLI tests: in a container, Toad rewrites a `localhost` URL to `host.docker.internal` for the tester, so the API must listen on all interfaces (`0.0.0.0`), not only `127.0.0.1`. If the project has an OpenAPI description, name it in `target.spec` (relative to `target.workdir`, which defaults to the project) so responses are checked against it; put request bodies and fixtures in that folder too. Say which endpoints may create, change or delete data, and how test data is cleaned up. Pass API tokens as credential references, never in URLs or scenarios.
6. Choose a canonical, absolute project path without symlinks or `..`. Call `setup_project` before the first project run. It creates `.toad/` without overwriting files and checks its ignore rules. Its `toad.yaml` holds project defaults (`web.url`, `cli.workdir`, `cli.program`, `cli.image`, `api.url`, `api.spec`, `api.workdir`, `cli.setup`, `api.setup`, `timeout_minutes`) and no secrets; fill it in with the user when they will test the same target repeatedly, so handoffs can omit `target`. If setup reports unsafe existing rules, inspect them and ask before changing user files. Treat handoffs, reports, screenshots, command output, retained workspaces, and receipts as potentially sensitive.

## Project handoff

Prefer `run_project_test` for project-local records. The following is the tool's argument object, not a request to paste into a shell:

```json
{
  "project_path": "/absolute/canonical/project",
  "handoff": {
    "version": 1,
    "kind": "web",
    "target": { "url": "http://localhost:3000" },
    "request": {
      "goal": "Verify the todo flow using disposable test data.",
      "scenarios": [
        { "name": "Create and complete", "steps": "Add a todo named Review, then complete it.", "expected": "The todo is marked complete and the active count decreases." }
      ]
    },
    "limitations": ["Do not modify existing user data."]
  },
  "screenshots": "paths"
}
```

For a CLI handoff use `"kind": "cli"` and `"target": { "workdir": "/absolute/canonical/project", "program": "node dist/cli.js" }`; replace the scenario with the actual commands, input, and expected output and exit codes. For an API handoff use `"kind": "api"` and `"target": { "url": "http://localhost:8080/api", "spec": "openapi.yaml" }`, with scenarios naming the requests and the expected status codes, headers and body fields, for example `{ "name": "Rejects a missing token", "steps": "GET /orders without an Authorization header.", "expected": "401 with a JSON error message, never 5xx." }`. `timeout_minutes` is optional. Give the run a short `title` (at most 120 characters) so people can find it in the viewer; keep the goal for the details. Name scenarios distinctly: results come back by name. Fields omitted from `target`, and the timeout, come from `.toad/toad.yaml`; the handoff wins where both are set. The server writes the effective handoff, the report, and the receipts under `.toad/runs/<run-id>/`. Verify paths returned by the tool rather than inventing them. Only a few runs execute at once on a machine; a call may wait for a free slot before starting, so do not retry it. The user can browse every project's runs in one localhost viewer; `setup_project` prints the command.

## Save suites to rerun

When the user wants tests to run again later, for example on every deploy or in CI, save the run you just made: call `save_suite_from_run` with the project path, the run id (the last part of the `run` folder `run_project_test` returned), a suite `name`, and optional `tags` and `writes`. It writes `.toad/suites/<name>.yaml` from the run's handoff and copies the run's valid recordings to `.toad/suites/<name>.recordings/`; it refuses a name already in use, never overwrites, and runs and commits nothing. Recordings exist only for single-command CLI and single-request API scenarios without credentials, installs, setup or PATH; web has none yet, and other scenarios are saved without one. Do not copy, edit or create recording files yourself; tell the user to review and commit the suite and its recordings folder. If a saved suite's scenario is later edited, its recording becomes stale: `toad run` and `toad ui` warn and ignore it, which is not an error. `toad run` replays valid saved recordings without a model; a stale or missing recording, or a replay whose assertion fails, is tested by the agent instead, and a new recording it captures is only proposed. The user accepts it with the `toad suites accept <run> --suite <name>` command `toad run` prints, or `toad run --update-recordings`; never accept or write recordings yourself. Without a suitable run, write the suite by hand instead: `.toad/suites/<name>.yaml` (lowercase name, letters, digits, `-`, `_` or `.`). A suite has the handoff's fields at the top level, not under `request`: `kind`, optional `title` and `target`, `goal`, `scenarios` (at least one, each with `name`, `steps`, `expected` and optional `tags`), optional `limitations`, `credentials` (references only), `allow_installs` and `timeout_minutes`. It also has optional `tags` and `writes`. Set `writes: true` only when a scenario creates, changes or deletes data; such a suite then runs only with `--allow-writes`, and a suite without it is told it is read-only. Leave out of `target` what `.toad/toad.yaml` already sets, so a deploy can override the URL. `.toad/suites/example.yaml` shows the format. The user runs suites with `toad run` (`--suite`, `--tag`, `--url`, `--junit`, `--summary`); it exits 0 on pass, 1 on a failure, 2 on an error and 3 when it cannot start. Saving a suite runs nothing: run a hand-written one once through `run_project_test` to check it works, and tell the user the `toad run` command. In CI, credentials come from the job's environment with `--env NAME,…`; the model key comes from the provider's variable, e.g. `ANTHROPIC_API_KEY`.

## Credentials and trust

- Never ask for or transmit secret values in chat, handoffs, scenarios, commands, logs, or reports. For supported web project tests, ask the user to put test-only values in the project's `.toad/.env` themselves, then reference names only, for example `"credentials": { "email": { "env": "TOAD_TEST_EMAIL" }, "password": { "env": "TOAD_TEST_PASSWORD" } }`. Names must be valid environment variable identifiers. The file uses `NAME=value` lines, not shell expansion. Never read it just to verify values; let the tool validate references.
- Project CLI and API tests also accept credential references. Only the named variables are passed to the sandboxed command; use `$NAME` in commands, never a value. Certain environment names that can alter process startup are reserved and rejected. A CLI program can transmit secrets over the shared network or write them to persistent artifacts, so use trusted programs and restricted, budget-limited test keys.
- Legacy `run_web_test` and `run_cli_test` use Toad's shared `agent/.faur/test-secrets.env`, not the project's store. The shared store may be exposed to the test process beyond the names requested; never use this as a silent substitute for project-owned or least-privilege credentials. Use it only with informed authorization and an accepted trust boundary.
- Project web credentials are resolved by name into a temporary per-run file, not a per-tool security boundary. Toad's agents, tools, subprocesses and same-user processes may access them. Screenshots, output, files and transformed values may expose secrets; redaction is best effort. Run only trusted workloads, and tell the user that artifacts can contain sensitive information. Cleanup may be incomplete after cancellation or failure; follow the server's reported cleanup guidance and do not remove files while processes might still use them.

## Execute and report

Call the discovered tool with the complete handoff. Toad runs can take minutes; respect progress and timeout behavior. Do not start duplicate runs merely because the first is slow. A failing test verdict is different from an execution or infrastructure error: inspect both `status` and `verdict`. `scenarios` gives each scenario's result by the name you gave it, and `cost` what Pi recorded for the run in US dollars; a scenario missing from the report is ERROR with `missing: true`. To rerun only what failed, send the same handoff with just those scenarios. Report PASS, FAIL, ERROR, or unknown accurately, including scenario-level evidence, actual versus expected behavior, and paths to reports and receipts. If the run is blocked, cancelled, times out, or has missing evidence, say what was not verified. Avoid reproducing secret-bearing output. Investigate failures before attributing them to the application; do not silently change the target or weaken scenarios to make a run pass.
